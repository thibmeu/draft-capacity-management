Bot rate limit is all you need

Abstract

Sites rate limit clients by address or by the intermediary they come through. Behind a shared intermediary, such as an AI agent platform, a VPN, or a network operator, every client then shares the same fate. This document describes the problem of limiting individual clients without requiring a stable identifier, and sketches a direction built on [MOLE-ARCH]: providers endorse their clients, and sites apply anonymous per-client limits. [WBA-HTTPSIG] can identify intermediaries for separate aggregate limits. It is a companion to [WBA-ABA].¶

1. Introduction

Agents are increasingly used in business and user workflows, including AI assistants, search indexing, content aggregation, and automated testing. Their relationship with websites is symbiotic. They need information from sites, and sites need signals to apply rate-limit policies. These can be binary, like allow or block when a site cannot serve traffic, or resource-based to ensure fair access to everyone.¶

Historically, most of these signals have been enshrined into deployments of internet protocols. A client needs an IP address to receive a response from an origin. Its TLS stack and browser behavior provide further signals. It provides a familiar User-Agent because middleboxes might otherwise filter its traffic (see [USER-AGENT-HISTORY]).¶

Recent developments break these patterns. Clients use proxies ([CONNECT-UDP], [CONNECT-IP], [OHTTP], or plain [HTTP]). As intermediaries make requests on behalf of users, the user's TLS stack may no longer be the one visible to the server. AI agents, local or remote, fetch and render information in place of browsers. User-Agent strings are still spoofed.¶

Sites need to apply policy despite these changes. Many approaches rely on obtaining a stable identifier. An address, including an [IPv6] address, is not necessarily a user. Blocking a shared IP range can affect everyone behind it. In enterprise settings, a client can identify as a workload [WIMSE-AIMS]. Intermediaries that can tolerate attribution can identify using [WBA-HTTPSIG]. Other approaches involve user authentication or authorization, such as [AAUTH] and [OAUTH-XAA].¶

While identification solves many problems, it should not be necessary just to limit a client's consumption. The problem is to give sites that control without requiring clients to disclose a stable identifier. This supports the user interests discussed in [INTERNET-FOR-END-USER].¶

1.1. Motivating use cases

In the cases below, traffic egresses through providers with existing user relationships. They have means to provide scarce endorsements for their users, which sites could use to apply rate-limit policies without learning who the user is.¶

  1. AI agent platforms concentrate traffic on a small set of IP addresses and make requests on behalf of users. One user's activity can affect others when a site can only limit the shared address or the platform as a whole.¶

  2. Network operators serve users behind shared IP ranges. Policies applied to an address range or an entire ASN give these users a shared fate.¶

  3. VPN providers and enterprise ZTNA gateways have a noisy neighbour problem. They may know their users, but should not have to expose them to each origin. An origin able to tell employees apart could single out an executive's activity for instance.¶

1.2. Related work

[WBA-ABA] shares the anonymous rate-limiting goal and the MOLE construction. This document is a companion to it. It focuses on providers that already have a relationship with their users, and on composing with an intermediary's [WBA-HTTPSIG] identity.¶

Poppy [POPPY] uses User IDs and sessions, including for anonymous browsing. [AAP] uses anonymous admission tokens and recommends a session afterwards, though it also allows a fresh token per request. Here, the aim is to maintain a client budget without linking its presentations.¶

MOLE will not solve every use case served by identifiers. Identity is still useful when an application needs it. Both MOLE and identity should be provided willingly by the client.¶

3. System

There is an intermediate system with MOLE and one Anchor. Essentially, the provider acts as Anchor and endorses its clients. The origin acts as Moderator. A Client redeems its Endorsement for a Credential, then presents and updates that Credential as it makes requests. The origin can apply a client rate limit or spendable budget. Where an intermediary identifies its forwarded traffic with Web Bot Auth, the origin can also limit that traffic in aggregate.¶

The two limits protect against different parties. The aggregate limit protects the origin from a dishonest provider, which controls how many Endorsements exist. The client limit gives fairness among an honest provider's users.¶

Because of MOLE's issuer-hiding property, this system can evolve to a second state where multiple providers endorse their clients within the same accepted Anchor Set. For instance, AI services could form one set, network operators another, and ZTNA providers a third. The intermediary may still be visible through Web Bot Auth or its egress address.¶

[[ Editor's note: Open points include:¶

  • Concurrent requests: one Credential cannot be used in parallel. One option is to issue several Credentials that split the budget.¶

  • Tunnels such as VPNs cannot add a Web Bot Auth signature today.¶

  • Scarcity: the same user could obtain Endorsements from two providers. ]]¶
